# ISEKAI Memory Phase 1~5·MCP·EKS 준비도 검증

세 독립 검토를 현재 구현과 다시 대조한 결과, Registry/Handoff 함수, PostgreSQL 쿼리, 6개 tool dispatch, stdio JSON-RPC 골격은 존재하지만 어느 주장도 E2E 실행으로 확인되지 않았다. “Phase 1~5 전체 완료”와 “6개 tool + auth + EKS 배포 준비 완료”는 구현 결함으로 성립하지 않는다. “독립 MCP 서버”는 stdio subset만 정적으로 확인되고 HTTP는 전용 REST이며, “Agent 직접 연결 가능”은 실제 client 연결 증거가 없어 미검증이다.

**Watch for:** **confirmed** project/scope/user authorization 부재로 유효 token 하나가 tenant 경계를 넘을 수 있다. **confirmed** Memory의 `artifact_digest` 의미가 Core 계약과 달라 정상 Core artifact 상호운용을 막는다. **likely** Dockerfile은 source와 README를 복사하기 전에 package build를 시도해 image build를 막는다. **confirmed** EKS 경로에는 migration 실행과 manifest placeholder 치환이 없다.

**Verdict**: NEEDS_CHANGES

## High-level view

6개 tool 이름과 Registry/Handoff SQL 경로는 연결되어 있다. 그러나 설계 완료 기준은 실제 HTTP 기동, 두 E2E 흐름, token 보안, stdio Agent 연결을 요구하며, `tests/`에는 빈 package marker만 있고 CI나 실행 기록도 없다.

stdio는 `initialize`, `ping`, `tools/list`, `tools/call`을 처리하지만 표준 인증·lifecycle·version 처리가 미완성이다. HTTP는 `/tools/{tool_name}` REST API로서 MCP Streamable HTTP/SSE가 아니다.

인증은 token 존재와 만료만 확인하고 project, user, scopes를 버린다. Artifact는 Core logical digest 대신 archive hash를 identity로 쓰며 내부 manifest/file/signature를 검증하지 않고, Handoff도 Core envelope·scope·stale·expiry 계약을 집행하지 않는다.

EKS YAML은 있지만 image build, DB migration, 환경변수, placeholder 치환이 배포 흐름으로 연결되지 않았다. 따라서 현재 상태는 “주요 코드 경로의 정적 존재”이지 “배포·상호운용 완료”가 아니다.

## Token 인증이 tenant 권한으로 이어지지 않는다

**confirmed.** HTTP middleware는 token hash와 expiry를 확인한 뒤 record를 폐기하고 dispatch에는 `(tool_name, arguments)`만 전달한다(`src/isekai_memory/server/http_handler.py:34-61`, `server/auth.py:18-48`, `main.py:14-31`). DB token의 `project_id`, `user_id`, `scopes`는 서비스에 도달하지 않는다(`migrations/versions/001_initial.py:96-106`, `store/queries.py:264-282`). list는 body의 project를 믿고 claim은 handoff UUID와 `pending`만 검사하므로 다른 project 조회·claim, read-only token의 write, `from_user`·`claimed_by`·`published_by` 위조가 가능하다(`handoff/service.py:81-109`, `store/queries.py:191-258`).

**confirmed.** stdio는 static token이 없으면 `auth_enabled=True`여도 authenticated로 시작하고, token을 설정하면 initialize params의 비표준 `auth_token`을 요구한다(`config.py:40-43`, `main.py:39-44`, `server/mcp_handler.py:19-26,96-103`).

## Registry와 Handoff가 Core 계약을 보존하지 않는다

**confirmed.** publish는 archive 전체 byte hash를 `artifact_digest`로 비교한다(`src/isekai_memory/registry/catalog.py:14-25`). Core는 이를 manifest/file tree의 logical digest로 정의하고 archive hash를 별도 `archive_digest`로 둔다(`../isekai-core/docs/core-protocol-specification.md:67-70,95-109`, `artifact-packaging-contract.md:92-95`). 정상 Core digest는 Memory에서 거부될 수 있고 Memory 저장값은 Core identity로 쓸 수 없다.

**confirmed.** Memory는 tar를 열지 않아 manifest schema/identity, file digest·size·mode, undeclared/path/link/special member, decompression limit, signature를 확인하지 않는다. fetch도 blob을 다시 hash하지 않고 DB digest 문자열만 비교하며 `max_archive_bytes`도 사용하지 않는다(`registry/catalog.py:14-37,86-126`, `config.py:37-49`). Core verifier의 대응 검사는 `../isekai-core/src/isekai/artifacts/verification.py:24-145`에 있다.

**confirmed.** Handoff push는 제출된 두 JSON의 pair digest만 검증한다(`handoff/service.py:14-43`). Core의 runtime schema, registered Task, correlation IDs, entity scope, lock/context binding, 별도 Handoff envelope 검증은 호출되지 않는다(`../isekai-core/src/isekai/execution/collaboration.py:18-91`, `../isekai-core/schemas/runtime-envelope.schema.json:1-96`). pull도 stale 검증이 없고 expiry는 168시간으로 고정된 채 list/claim에서 무시된다(`handoff/service.py:44-48,102-137`, `store/queries.py:191-258`).

## Tool·policy·retry의 advertised 동작이 집행되지 않는다

**confirmed.** 6개 `inputSchema`는 상세 제약을 선언하지만 stdio와 HTTP는 object 여부만 확인한다(`server/tools.py:7-127`, `server/mcp_handler.py:126-137`, `server/http_handler.py:73-119`). 잘못된 입력과 과대 payload가 service/DB까지 도달하며, `MemoryToolError.code`도 stdio에서 `-32000`으로 대체되어 protocol error와 tool failure가 섞인다(`server/mcp_handler.py:63-75,147-154`).

**confirmed.** policy CRUD가 없고 후보는 `published_at DESC`의 첫 만족 version이라 최고 semver가 아니다; prerelease/build와 `^`, `~`도 지원하지 않는다(`store/queries.py:81-126`, `registry/policy.py:10-77,118-129`). Artifact와 Handoff의 unique-key conflict는 새 payload digest를 기존 값과 비교하지 않아 서로 다른 요청도 성공한 retry로 처리한다(`registry/catalog.py:39-57`, `handoff/service.py:69-78`, `store/queries.py:15-47,129-188`).

**confirmed.** migration에는 kind/status/digest 및 archive storage 일관성 CHECK가 없어 transport validation 부재를 DB가 보완하지 못한다(`migrations/versions/001_initial.py:18-107`).

## stdio subset, HTTP REST, Core adapter 부재

**confirmed.** stdio는 handshake와 tools capability가 있지만 initialize lifecycle을 강제하지 않고 client version을 협상하지 않으며 frame 제한도 `readline()` 뒤 문자열 길이로 검사한다(`server/mcp_handler.py:28-43,81-111`). 특정 Agent 연결은 **미검증**이다. HTTP에는 `/mcp`, JSON-RPC, SSE/Streamable session과 MCP headers가 없고 plain REST만 있다(`server/http_handler.py:73-119`); 설계의 “stdio + HTTP/SSE”와 다르다(`docs/design.md:484-509`).

**confirmed.** README의 Core 자동 연동 설명과 달리(`README.md:31-48`), Core에서 `isekai-memory`, `memory_artifact`, `memory_handoff`, `auto_push`, `server_url` 심볼이 없고 설계도 Core 변경을 Phase 6으로 둔다(`docs/design.md:606-654`).

## EKS 파일은 rollout 가능한 배포 단위가 아니다

**likely.** Dockerfile은 `pyproject.toml`만 복사하고 첫 `pip install .`을 실행하지만 metadata는 `README.md`, wheel은 `src/isekai_memory`를 요구한다(`Dockerfile:10-20`, `pyproject.toml:5-9,28-29`). README는 두 번째 install 전에도 복사되지 않는다. 실제 build는 **미검증**이다.

**confirmed.** 앱은 `ISEKAI_MEMORY_DATABASE_URL`, Alembic은 `DATABASE_URL`을 읽고 startup·Docker·Deployment에는 migration 실행이 없다(`config.py:19-32`, `migrations/env.py:7-10`, `Dockerfile:28-33`, `k8s/deployment.yaml:20-25`). `/ready`는 `SELECT 1`만 확인해 schema 없는 DB도 ready로 표시할 수 있다(`store/database.py:36-42`).

**confirmed.** image/host/certificate는 미치환 placeholder이고 Helm/Kustomize/script, secret·token·policy provisioning이 없다(`k8s/deployment.yaml:16-25`, `k8s/ingress.yaml:1-18`). ClusterIP Service에는 external LB annotation이 붙어 ALB Ingress와 역할도 맞지 않는다(`k8s/service.yaml:1-21`).

## 완료 주장을 뒷받침할 실행 증거가 없다

**confirmed.** `tests/`에는 `tests/__init__.py`만 있고 CI workflow도 없다. PostgreSQL migration, Registry/Handoff E2E, auth, server 기동, 공식 MCP client, image build와 Kubernetes rollout은 모두 **미검증**이다(`docs/design.md:635-654`).

## 최소 보완 순서

1. Core digest/envelope, 지원 MCP transport, auth principal 계약을 고정한다.
2. project/organization/user/scope authorization을 모든 tool에 fail-closed로 적용한다.
3. Docker build와 DB URL을 고치고 migration 단일 실행 경로를 만든다.
4. Artifact archive 검증과 Handoff schema/correlation/lock/context/stale 검증을 구현한다.
5. input schema·크기 제한과 MCP protocol/tool error를 transport 경계에서 집행한다.
6. idempotency, expiry, 최고 semver, policy/token 관리 경로를 완성한다.
7. stdio 표준 호환을 맞추고 HTTP MCP를 구현하거나 지원 주장을 축소한다.
8. 배포 template·secret·probe를 완성하고 DB E2E, 공식 client, image, migration, EKS smoke test를 CI에서 통과시킨다.
