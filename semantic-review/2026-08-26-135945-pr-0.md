# 복구 가능한 handoff lease와 완료 영수증

Revision 003은 기존 일회성 handoff pull에 토큰 기반 lease, response-loss replay, ack/nack 영수증을 추가한다. `FOR UPDATE`로 claim 경쟁을 직렬화하고 원문 claim token 대신 SHA-256 digest만 저장하며, 프로젝트와 actor를 토큰 검증 조건에 포함한다. 그러나 잠금 획득 전에 고정된 PostgreSQL 트랜잭션 시각으로 lease를 판정하고, ack/nack 요청에 이미 반환한 `claim_generation`을 요구하지 않아 만료 경계와 재획득 경계에서 소유권 fencing이 깨진다.

Watch for: **[High, confirmed]** 잠금 대기 뒤에도 `now()`가 트랜잭션 시작 시각을 가리켜 만료된 lease가 유효하게 처리될 수 있음; **[High, confirmed]** ack/nack에 generation fencing이 없어 이전 generation의 지연 요청이 재획득된 claim을 완료할 수 있음; **[Low, confirmed]** 낮은 엔트로피 claim token도 허용되어 저장 digest가 오프라인 추측에 취약함; **[Medium, confirmed]** check constraint와 일반 index를 한 migration에서 생성해 운영 중 쓰기를 장시간 막을 수 있음; **[Medium, confirmed]** 신규 claim/get/ack/nack 및 migration 동시성 회귀 테스트가 없음.

**Verdict**: NEEDS_CHANGES

## High-level view

Recoverable claim은 `(handoff, project, actor, token digest)`가 활성 lease와 일치할 때 같은 payload를 재생하고, lease가 끝나면 다른 claimant가 행 잠금 아래 새 generation을 얻는다. 만료 판단 시각이 lock wait를 반영하지 않아 실제 벽시계와 데이터베이스 판정이 갈라진다.

Ack와 nack은 상태 전이와 영수증 생성을 한 transaction에 묶어 response loss 뒤 동일 요청을 재생한다. API가 generation을 입력으로 받지 않아 같은 token이 만료 뒤 다시 claim되면 지연된 이전 요청과 현재 요청을 구분하지 못한다.

HTTP 경로는 인증 token의 project와 요청 project를 맞춘 뒤 query에도 project와 actor를 전달한다. 원문 claim token은 저장하지 않지만 형식과 길이만 제한하여 반복 문자열 같은 추측 가능한 token도 capability로 받아들인다.

Revision 003 downgrade는 acknowledged를 revision 002가 표현 가능한 claimed로 바꾸어 소비 완료 의미를 보존한다. 반면 upgrade의 constraint 재생성과 일반 index 구축은 큰 live table에서 쓰기 중단을 유발할 수 있다.

현재 테스트는 push idempotency와 legacy pull, schema revision 확인만 다룬다. PostgreSQL row-lock 대기, response-loss replay, wrong/stale token, ack/nack 경쟁, lease 만료, project isolation, revision 003 왕복은 자동 검증되지 않는다.

<summary>Issues (5)</summary>

1. **[High, confirmed] Transaction-stable lease clock** — `queries.py`의 `claim_handoff_lease`·`acknowledge_handoff`·`nack_handoff`가 lock wait 전 `now()`로 만료를 판단해 실제 만료 뒤 claim을 거절하거나 ACK/NACK를 수락할 수 있다. 잠금 획득 후 실제 현재 시각으로 비교하고 lock-wait 통합 테스트를 추가해야 한다.
2. **[High, confirmed] Missing generation fencing** — `tools.py`의 ack/nack 계약과 `queries.py` 완료 조건에 `claim_generation`이 없어, 이전 generation의 지연된 ACK/NACK가 동일 token의 재획득 generation을 종료할 수 있다. generation을 요청·receipt identity·UPDATE predicate에 포함해야 한다.
3. **[Low, confirmed] Guessable claim token accepted** — `tools.py::CLAIM_TOKEN`은 32자 반복 문자열도 허용하고 `service.py::_claim_token_digest`는 무키 SHA-256을 사용해 DB 노출 시 저엔트로피 token을 오프라인 추측할 수 있다. CSPRNG 발급/계약과 서버 비밀 기반 digest를 검토해야 한다.
4. **[Medium, confirmed] Blocking revision 003 DDL** — `003_recoverable_handoff_leases.py::upgrade`가 constraint를 즉시 검증하고 일반 index를 생성해 큰 live table의 handoff 쓰기를 막을 수 있다. staged validation/concurrent index 또는 maintenance window를 사용하고 upgrade/downgrade 순서를 고정해야 한다.
5. **[Medium, confirmed] Recoverable path untested** — 현재 테스트는 claim/get/ack/nack, competing claimants, response-loss replay, stale token/generation, project isolation, revision 003 왕복을 실행하지 않는다. 실제 PostgreSQL 기반 동시성·migration suite를 추가해야 한다.

## Row lock 뒤에도 과거 시각으로 판정되는 lease

**[High, confirmed]** `claim_handoff_lease`, `acknowledge_handoff`, `nack_handoff`는 transaction을 연 뒤 `SELECT ... FOR UPDATE`에서 `now() AS db_now`를 읽어 lease와 handoff 만료를 판단한다 (`src/isekai_memory/store/queries.py:225-304`, `326-386`, `397-470`). PostgreSQL의 `now()`는 lock 획득 시각이 아니라 transaction 시작 시각으로 고정되므로, 행 잠금으로 경쟁자를 직렬화한 뒤에도 만료 기준은 lock wait 전 값이다.

Claimant A가 행 잠금을 60초 보유하고 B가 30초 lease 만료 전에 transaction을 시작해 대기하면, B는 실제 만료 뒤 잠금을 얻어도 기존 claim을 active로 보고 거절할 수 있다 (`queries.py:240-265`). Ack/nack도 만료 전에 transaction을 시작했다면 실제 만료 뒤 완료를 수락할 수 있다 (`queries.py:358-364`, `440-446`). 새 claim의 `claimed_at`과 `claim_lease_expires_at`도 과거 기준을 사용해 commit 시 이미 만료됐거나 요청보다 짧은 lease를 반환할 수 있다 (`queries.py:281-289`).

잠금 획득 뒤 별도 statement에서 `clock_timestamp()`를 읽거나 상태 전이 UPDATE가 실제 현재 시각을 비교하도록 바꾸고, lock wait를 의도적으로 발생시키는 PostgreSQL 통합 테스트가 필요하다.

## 반환만 되고 fencing에는 쓰이지 않는 claim generation

**[High, confirmed]** 새 claim마다 `claim_generation`은 증가하고 response에도 반환되지만 (`src/isekai_memory/store/queries.py:281-304`, `src/isekai_memory/handoff/service.py:181-205`), ack/nack 스키마는 `project_id`, `handoff_id`, `claim_token`만 받는다 (`src/isekai_memory/server/tools.py:147-170`). 완료 query도 actor/token digest만 비교하며 generation predicate가 없다 (`queries.py:326-386`, `397-470`). Receipt는 generation을 기록하지만 unique identity에서 제외되어 fencing에 쓰이지 않는다 (`migrations/versions/003_recoverable_handoff_leases.py:59-86`).

Actor A가 token T로 generation 1을 claim한 뒤 lease가 만료되었지만 ACK가 네트워크에서 지연될 수 있다. B가 generation 2를 claim했다가 만료시키고 A가 같은 T로 generation 3을 다시 claim하면 receipt가 아직 없으므로 재획득된다 (`queries.py:267-289`). 이때 generation 1의 ACK가 도착하면 현재 actor/token이 다시 일치해 generation 3을 acknowledge한다. NACK에도 같은 문제가 있어 이전 요청이 새 시도를 종료할 수 있다.

Claim/get/ack/nack 계약과 receipt 조회·상태 UPDATE에 `claim_generation`을 포함하고, 만료 → 경쟁 claim → 만료 → 원 token 재획득 사이에 이전 ACK/NACK를 지연시키는 테스트가 필요하다.

## Digest 저장은 원문을 숨기지만 token 강도를 보장하지 않음

**[Low, confirmed]** 서비스는 원문 대신 SHA-256 digest를 저장하지만 (`src/isekai_memory/handoff/service.py:176-178`), schema는 32~256자의 허용 문자만 검사해 `aaaaaaaa...` 같은 저엔트로피 token도 수락한다 (`src/isekai_memory/server/tools.py:10`, `120-170`). DB snapshot이나 receipt가 노출되면 이런 digest는 빠르게 역추측할 수 있다. 별도 HTTP 인증과 project/actor 일치도 필요하므로 digest 노출만으로 cross-project claim은 되지 않지만, 같은 principal 자격 증명까지 노출되면 claim capability의 추가 방어선이 사라진다.

서버가 CSPRNG token을 발급하거나 최소 128~256비트 무작위 값 계약을 강제하고, 저장 digest에는 서버 비밀 기반 HMAC을 검토해야 한다. Project isolation은 `authorize_tool`의 요청-project 검사와 dispatcher의 `authorized_project_id` 전달로 query까지 유지된다 (`src/isekai_memory/server/auth.py:71-105`, `src/isekai_memory/main.py:39-63`); 다른 project의 동일 handoff UUID/token/actor 조합을 거부하는 통합 테스트가 필요하다.

## Live upgrade에서 쓰기를 막는 revision 003 DDL

**[Medium, confirmed]** upgrade는 status check constraint를 즉시 교체하고 두 PostgreSQL index를 일반 `CREATE INDEX`로 만든다 (`migrations/versions/003_recoverable_handoff_leases.py:18-58`). Constraint 변경은 강한 table lock과 검증 scan을 요구하고 non-concurrent index build는 쓰기를 막는다. 큰 운영 table에서는 push/claim/ack/nack가 lock timeout 또는 장시간 지연될 수 있고, transaction-stable timestamp 결함과 결합하면 대기 중 lease 의미도 악화된다.

Maintenance window를 명시하거나 check를 `NOT VALID`로 추가한 뒤 validate하고, transaction 밖 concurrent index build를 사용하는 staged migration이 필요하다. Downgrade의 acknowledged → claimed 변환 (`003_recoverable_handoff_leases.py:92-111`)은 소비된 handoff를 pending으로 되돌리지 않지만, 신·구 애플리케이션 실행 순서와 revision 왕복을 배포 문서와 테스트로 고정해야 한다.

## Recoverable 경로를 실행하지 않는 테스트 모음

**[Medium, confirmed]** `tests/test_handoff.py`는 envelope 상관관계, push 인자, push retry만 검증하고 `tests/e2e_smoke.py`는 revision 003 준비 상태 뒤 legacy `memory_handoff_pull`만 사용한다. 현재 테스트 전체에서 recoverable endpoint나 lease query 호출이 없다. 핵심 계약이 PostgreSQL transaction과 row lock에 있으므로 mock 단위 테스트만으로는 위 결함을 잡을 수 없다.

Not tested: **[Medium, confirmed]** 동시 claim 승자 단일성, active response-loss replay, lease 만료 전후 get, wrong/stale token, stale generation ACK/NACK, 동일 ack/nack 재시도와 다른 reason 재시도, ack 대 nack 경쟁, legacy pull 대 recoverable claim 경쟁, project/actor 격리, low-entropy token 정책, revision 002→003→002 상태 보존, lease보다 긴 lock wait. 실제 PostgreSQL 통합 suite가 필요하다.
