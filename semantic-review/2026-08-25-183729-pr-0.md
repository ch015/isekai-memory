# Modern-only MCP 2026-07-28 transport contract

Phase 6-0 replaces the handshake-era MCP path with stateless `server/discover`, per-request metadata, and strict HTTP routing headers while retaining the existing tool dispatcher and PostgreSQL service behavior. The `DiscoverResult`, HTTP header rules, README, and design document agree on the 2026-07-28 contract, and the HTTP E2E exercises real artifact, policy, and handoff operations. The remaining defects are in malformed JSON-RPC envelope handling and the strength of the stdio PostgreSQL evidence rather than in the chosen protocol shape. **Watch for:** **[High, confirmed, Phase 6-0 blocker]** malformed id-less envelopes are silently discarded and invalid identifier types are accepted; **[Medium, confirmed, Phase 6-0 blocker]** the stdio E2E never executes a database-backed tool; **[Low, confirmed]** tests do not pin all required discovery fields or the literal protocol version.

**Verdict**: NEEDS_CHANGES

## High-level view

The production protocol is modern-only: `PROTOCOL_VERSION` has one value, every routed method validates `_meta`, removed handshake methods fall through to method-not-found, and no legacy version-negotiation path remains. HTTP requires `MCP-Protocol-Version` and `Mcp-Method`, requires an exact `Mcp-Name` only for `tools/call`, and returns controlled routing errors for missing or mismatched headers.

The discovery payload has `resultType`, `supportedVersions`, `capabilities`, optional `instructions`, `ttlMs`, and `cacheScope`, with server identity confined to the namespaced `_meta` entry. **[Low, confirmed]** tests assert only part of that contract and derive expected versions from the production constant, so field or version drift can pass the suite.

**[High, confirmed, Phase 6-0 blocker]** `McpProtocolHandler.handle` decides that any object without `id` is a notification before validating the JSON-RPC envelope. Invalid `jsonrpc` or `method` values can therefore receive no error response, while present but structurally invalid IDs are accepted and echoed.

The HTTP smoke is meaningfully PostgreSQL-backed because successful MCP calls publish and fetch an archive, mutate and resolve policy, and push, list, and pull a handoff. **[Medium, confirmed, Phase 6-0 blocker]** the stdio smoke opens a pool but sends only discovery, tool listing, and rejected `initialize`, all of which avoid database tables and therefore pass against an unmigrated database.

The design explicitly leaves one-shot handoff claim recovery to Phase 6-4 and prevents `ContextService` from claiming directly. **[Confirmed, Phase 6-4]** this is a documented later-phase limitation, not a Phase 6-0 defect or a blocker for standalone Phase 6-1 `MemoryClient`, configuration, or credential work; Phase 6-0 should not be marked complete until the two blockers above are fixed.

## Discovery and routing expose only the 2026-07-28 model

`protocol.py::discover_result` returns the required cacheable discovery shape and places `SERVER_INFO` only at `_meta["io.modelcontextprotocol/serverInfo"]`. `mcp_handler.py::_route` exposes `server/discover`, `tools/list`, and `tools/call`; `initialize`, `notifications/initialized`, and `ping` have no compatibility branch. The deprecated `Settings.auth_static_token` accepts an old configuration key but does not create a second protocol or authentication execution path.

`http_handler.py::mcp_endpoint` ties `Mcp-Method` to the JSON-RPC method, requires `Mcp-Name` to equal `params.name` for `tools/call`, and rejects that header for every other method. Transport tests cover missing headers, unsupported versions, method/version disagreement, absent `Mcp-Name`, and forbidden `Mcp-Name` on discovery.

**[Low, confirmed]** `test_server_discover_returns_cacheable_schema_shape` does not assert `capabilities` or `instructions`, and its supported-version assertion compares `SUPPORTED_VERSIONS` to a result produced from that same object. Pin `PROTOCOL_VERSION == "2026-07-28"` and assert the complete discovery key/value contract, including capabilities and namespaced identity.

## Invalid request objects can disappear as notifications

`mcp_handler.py::McpProtocolHandler.handle` sets `notification = "id" not in request` before checking `jsonrpc` and `method`. The invalid-envelope branch then returns `None` whenever `id` is absent, so a 1.0 request or one with a non-string method is treated as a notification rather than returning JSON-RPC `-32600` with a null identifier. This is **[High, confirmed, Phase 6-0 blocker]** because HTTP turns the suppressed response into 202 and stdio emits no frame.

The handler also never checks the type of a present `id`. Arrays, objects, and booleans can reach dispatch and be echoed even though a JSON-RPC identifier is limited to string, number, or null. Validate the envelope and identifier before classifying a request as a valid notification, and add direct handler plus HTTP/stdio cases for invalid `jsonrpc`, invalid or missing method, and invalid identifier types.

## Stdio smoke proves startup but not migrated PostgreSQL behavior

`tests/stdio_e2e_smoke.py::main` launches the real module entry point, which reaches `main.py::run_stdio` and opens an asyncpg pool. Its frames are `server/discover`, `tools/list`, and `initialize`; none invokes `ToolDispatcher` or queries a table. Because `init_pool` checks connectivity but not Alembic revision or required relations, the test can pass against an empty PostgreSQL database. This is **[Medium, confirmed, Phase 6-0 blocker]** against the required meaningful PostgreSQL stdio evidence.

Add a valid `tools/call` frame for a deterministic read such as `memory_handoff_list` or artifact resolution and assert a non-error `CallToolResult` with the expected structured shape. That crosses stdio framing, the production dispatcher, schema validation, the local-principal boundary, and an actual PostgreSQL query.

## HTTP smoke crosses the real service boundary

`tests/e2e_smoke.py` sends modern MCP requests through the authenticated HTTP endpoint and reaches real PostgreSQL mutations and reads. Publish retry, policy resolution and deletion, archive fetch verification, handoff idempotency and claim, and final empty resolution make a metadata-only false positive unlikely. The routing headers are consistency metadata rather than credentials; bearer verification remains in middleware and tool authorization remains in `ToolDispatcher`.

## Recoverable claims remain a Phase 6-4 gate

`docs/design.md` states that pull is a one-shot conditional claim without lease, acknowledgement, or replay and blocks direct `ContextService` claiming until that contract exists. This is **[Confirmed, Phase 6-4]** recoverable-claim work rather than a regression in the protocol correction. Standalone Phase 6-1 `MemoryClient`, configuration, and credential handling may begin in parallel because discovery, headers, tool listing, and the credential boundary are stable; inbound automatic synchronization must remain disabled, and Phase 6-0 remains open until malformed-envelope handling and stdio E2E evidence are corrected.
