# M10 — 공용 연결 키와 Memory 중심 프로젝트·활동 관리

2026-09-23 상태: 아래는 2026-09-16의 과거 제안이며 현재 운영 계약이 아니다.
현재는 사용자별 인증·멤버십을 집행하며 공용 키로 모든 사용자를 동일 권한으로 취급하지 않는다.
프로젝트 디렉터리·자료·자동 이력의 구현 범위는 [현재 공유 계약](project-sharing.md)과
[다중 사용자 운영](multiuser-operation.md)을 따른다. 이 계획을 새 배포 절차로 사용하지 않는다.

합의: 2026-09-15. 문서 정리: 2026-09-16. 상태: **계획 확정 / 기능 구현 전**.
이 문서는 기존 M10의 광범위한 회원 관리보다 아래 사용 흐름을 우선한다.
기존 M7–M9 구현과 검증 기록을 소급해서 변경하지 않는다.

## 합의한 목표

사용자 계정, 로그인, 사용자별 키 발급, Nunchi 인증/RBAC은 이번 범위에서 제외한다.
운영자가 발급하는 서버 공용 API 키 하나를 각 PC의 Core에 한 번 설정한다.
키는 프로젝트에 종속되지 않으며, 같은 키를 가진 접속자는 동일한 권한을 가진다.
사용자는 임의 프로젝트를 등록하고 Memory의 전체 목록과 작업 활동을 조회할 수 있다.

```text
공용 키 1개 발급 → 각 Core에 서버 주소·키 설정
    → 로컬 프로젝트 등록 → Memory 중앙 등록부에 저장
    → Core의 작업·세션·인계·메모리 변경 보고
    → watch: 전체 / 이 PC에 연결된 프로젝트
    → watch --manage: 전체 활동과 명시적 관리 작업
```

“내 프로젝트”라는 사람 기준 표현은 사용하지 않는다.
출처는 host_id / workspace_id / session_id로 표시하며 검증된 사람의 신원이 아니다.
같은 키를 공유하므로 출처 ID의 위변조 방지나 사용자별 감사 부인 방지를 보장하지 않는다.
--manage는 UI 선택이지 별도 보안 권한이 아니다. 기존 파괴적 작업 확인은 유지한다.

## 현재 병목과 재사용할 구현

- Core ProjectRegistry는 로컬 JSON 저장소이며 서버에 등록하지 않는다.
- Memory 013 / 82개 도구에는 업무 프로젝트 등록·전체 목록 API가 없다.
  memory_repo_list는 Foundation/Preset 배포 저장소 목록이다.
- Memory auth_enabled=false는 모든 요청을 local-stdio로 처리한다.
- M8 인수 대상자 목록·적격성은 access_tokens를 조회하므로 공용 키만 붙이면 완성되지 않는다.
- Core 콘솔 연결과 실제 Project/Lock의 Memory 기능 opt-in은 별개다.
- M9 이벤트는 일부 협업 변경의 프로젝트별 feed다. 전체 프로젝트 활동·모든 Core 행위를 포괄하지 않는다.
- 기존 MCP transport, bounded pagination, idempotency, outbox, lease fencing,
  TUI 상세·관리 화면을 재사용한다. 비용·청구량 기능은 확장하지 않는다.

## 설계 원칙

### 공용 키와 기존 인증

- 새 shared-key 모드를 명시한다. 기존 프로젝트별 토큰 모드와 무인증 개발 모드를
  구분하고 설정 충돌·공용 키 누락은 시작 오류로 처리한다. 무인증으로 자동 전환하지 않는다.
- 공용 키는 충분히 긴 난수로 서버 운영 CLI에서 발급하고 원문은 한 번만 전달한다.
  서버에는 검증용 해시, Core에는 owner-only credential 파일을 저장한다.
- 키 발급·교체는 서버 운영 명령으로 제한한다. 공개 MCP 조회나 로그, Git,
  Project/Lock, argv, Compose YAML에 원문을 넣지 않는다.
- 같은 키로 모든 업무 프로젝트에 접근한다. 이후 Nunchi는 이 접속 경계에 추가한다.
  기존 actor/user 기록을 공용 사용자로 덮어쓰거나 기존 프로젝트별 토큰 검증을 약화하지 않는다.
- 기존 auth_static_token은 deprecated 설정이므로 그대로 되살리지 않는다.
- 현재 Core는 Bearer의 비-loopback HTTP를 차단한다. 공용 키 LAN 운영에는
  별도의 명시적 연결별 HTTP 예외가 필요하다. 기본은 HTTPS이며, 예외 사용 시 키와
  내용이 평문 전송된다는 경고를 표시한다. 신뢰 LAN 밖에서는 TLS/VPN을 사용한다.

### 프로젝트와 PC별 작업폴더

- Memory가 업무 프로젝트 목록의 원본이다. Core 로컬 목록은 캐시·경로 바인딩으로 축소한다.
- 프로젝트: 안정적 project_id, 표시 이름, 상태, 등록/갱신 시각, 선택적 정제된 Git 원격 메타데이터.
- workspace: project_id, host_id, workspace_id, 표시 이름, 마지막 관측 시각과 연결 상태.
- session: workspace와 실행 세션의 연결. host/workspace는 로그인 계정이나 역할이 아니다.
- 같은 프로젝트의 여러 clone/worktree는 프로젝트 하나 + workspace 여러 개로 표현한다.
  폴더명만으로 동일 프로젝트를 추정하지 않는다. 기존 프로젝트 선택/새 등록을 분명히 구분한다.
- 절대 로컬 경로는 기본적으로 해당 Core에만 저장한다. 서버에는 workspace ID와 표시 이름을 보고한다.
  Git URL의 사용자정보·토큰·query는 제거한다. 서버는 PC 폴더를 탐색하거나 임의 경로를 실행하지 않는다.
- 기존 project_id 문자열과 업무 기록을 보존한다. 신규 ID 발급은 UUID 등 안정적 ID를 사용한다.
  기존 데이터의 project_id를 수집해 “기존 기록에서 발견” 항목으로 이관할 수 있으나,
  사용자·PC·프로젝트 명칭을 추측해서 채우지 않는다.

### 등록과 실행을 연결하되 자동 권한 확대 금지

- 서버 연결은 호스트 전역 1회, 프로젝트 등록은 폴더별 1회로 통합한다.
- 등록 시 중앙 등록과 PC 바인딩을 완료하고 등록/동기화 상태를 반환한다.
- Core의 기본 작업 메타데이터 보고는 등록 절차에서 범위와 수집 여부를 명확히 안내한다.
  소스 본문·체크포인트 업로드, 자동 인계, 로컬 실행 승인은 별도 동의/기존 권한 절차를 유지한다.
- Project/Lock 적용을 우회하지 않는다. 콘솔 연결 파일만 추가하고 실제 실행 연동까지
  완료됐다고 표시하지 않는다.
- 오프라인 등록은 “로컬 대기”로 표시하고 안정적 요청 ID로 재전송한다.
  서버 확인 전 “등록 완료”로 표시하지 않는다. 재시도는 동일 프로젝트·workspace를 중복 생성하지 않는다.
- 기존 memory-projects.json 항목은 명시적 가져오기로 전환한다. 조회만으로 서버 등록을 만들지 않는다.

### 관측과 인수인계

- 첫 범위: 프로젝트 등록/변경/보관, workspace 연결/해제, 세션 시작/종료/상태,
  Core 작업 시작/완료/실패, 인계/수신 확인/claim/반납/완료, 메모리 제안/검토/수정.
- 일반 heartbeat와 토큰 단위 변화는 이벤트를 무한 누적하지 않고 최신 상태/집계를 유지한다.
- 임의 셸·Core 밖 CLI 대화는 자동 관측되지 않는다. 보고 시각·서버 수신 시각·미관측/지연을 구분한다.
  원문 프롬프트·키·파일 본문·임의 도구 인자는 활동 feed에 저장하지 않는다.
- 기존 M8 사용자별 1:N 기능은 보존한다. shared-key 모드에서는 사람인 척하는
  가짜 access_tokens를 만들지 않는다. workspace 기반 임시 인계 대상과 수신 확인을
  명시적으로 모델링하고, 해당 모드에 한해 등록 workspace로 대상 적격성을 검증한다.
- 공용 키는 공통 접근 키일 뿐 개별 작업 claim/lease/session capability를 대체하지 않는다.
  1:N 독립 확인, 단일 활성 소유자, generation fencing, 확인 후 로컬 준비 규칙을 유지한다.
- 업무 변경과 서버 활동 기록은 같은 트랜잭션으로 저장한다. Core 보고는 durable outbox로 재시도한다.
  등록 이벤트·메모리 변경 등 기존 M9에 없는 범위를 명시적 event schema로 보완한다.

## 단계별 작업과 완료 기준

| 단계 | 주요 책임 | 작업 | 완료 기준 |
| --- | --- | --- | --- |
| M10-1 | Memory + Core 연결 설정 | 공용 키 발급/검증/교체, 모드 분리, 1회 전역 연결, LAN 예외 | 같은 키로 서로 다른 프로젝트 조회 가능; 누락/오류 키 거부; 원문 유출 없음 |
| M10-2 | Memory | 프로젝트·workspace 등록부, 등록/목록/상세/보관, 기존 기록 이관 | 빈 프로젝트도 목록에 표시; 다중 PC 바인딩·중복 재시도 처리 |
| M10-3 | Core | 연결/프로젝트 등록 절차, 로컬 경로 바인딩, 서버 목록 수신, 대기 outbox | A PC 등록이 B PC 목록에 나타남; 폴더별 연결 키 입력 불필요 |
| M10-4 | Memory + Core | 전체 활동 feed/요약, 실행 메타데이터 보고, workspace 인계 호환 | 서로 다른 프로젝트의 작업·인계·메모리 변경이 통합 조회됨; 출처/관측 공백 표시 |
| M10-5 | Core watch | 서버 기준 전체/이 PC 필터, 전체 활동 타임라인, 기존 상세·관리 연결 | 새 PC는 주소·키만 설정해 서버 프로젝트 조회; 선택하지 않은 프로젝트 활동도 표시 |
| M10-6 | 양쪽 + 배포 | 최소 수용 테스트, migration/기존 토큰 호환, 재개·운영 안내 | 두 PC/서로 다른 경로/동일 키 시나리오 완료; 코드/배포/실제 확인 상태를 구분해 인계 |

첫 사용 가능한 구간은 M10-1 → M10-2 → M10-3 + M10-5의 목록 화면이다.
이후 M10-4와 전체 활동 화면을 완성한다. 화면 먼저 만들고 중앙 등록을 나중에 붙이지 않는다.
외부 인증·광범위한 조직 회원 관리·외부 connector는 이 완료 경로에 끼워 넣지 않는다.

## API/저장소 작업 단위 — 신규 설계 후보, 아직 사용 불가

- server information: 서버 ID, auth mode, 지원 capability, namespace 기본값.
- memory_project_register / list / get / archive: 기본 등록은 workspace 바인딩과 원자적으로 처리.
- memory_workspace_register / list / detach: 기존 프로젝트에 PC별 경로 연결·해제.
- memory_activity_append / list: 검증된 Core 업무 이벤트 및 전체 프로젝트 catch-up.
- 전체 목록의 기본 요약은 서버가 페이지 단위로 집계한다.
  Core가 프로젝트마다 overview/presence/usage를 순회하는 구조를 기본 경로로 두지 않는다.
- 불투명 cursor, 필터 결박, event_id 중복 방지, 버전 충돌, bounded limit/retention을 적용한다.
  단순 timestamp/MAX(id) 기반 cursor로 늦게 commit된 이벤트를 누락시키지 않는다.
- 초기 조회 watermark → 상태 snapshot → catch-up 계약을 정의한다.
  화면 수락 후 cursor 저장, 보존 공백 시 전체 재조회, 서버 재시작 후 재개를 유지한다.
- schema 013 이후의 가산적 migration으로 진행하며 실제 revision 번호는 구현 시작 시
  양쪽 최신 Git/migration head를 확인한 뒤 결정한다. 기존 테이블/데이터 초기화 금지.
- 수정 접점: Memory config/main/server auth/tools/dispatch, migrations/store,
  continuity eligibility/events, Core memory config/client/coordinator/console registry/portfolio.
  사용자 권한과 host 출처 정보를 분리하고 기존 토큰 모드 테스트를 보존한다.

## 최소 수용 검증

1. 동일 키의 두 클라이언트가 서로 다른 프로젝트 및 같은 프로젝트의 다른 workspace를 등록.
2. 별도 수동 프로젝트 JSON 없이 두 클라이언트의 목록이 일치하고 “이 PC” 필터만 다름.
3. 키 누락/오류/교체 후 기존 키 거부; 기존 프로젝트별 토큰 모드의 격리 유지.
4. 중복 등록, 응답 유실 후 재시도, 오프라인 후 재접속에 중복 프로젝트·이벤트가 없음.
5. 등록·작업·인계·메모리 변경이 전체 활동에 나타나며 페이지 밖 프로젝트도 관측.
6. 임시 workspace 1:N 인계의 개별 확인과 동시 claim fencing 유지.
7. 원격 경로는 해당 PC에서만 실행 가능; 목록 조회로 파일 업로드·clone·worker 실행 안 함.
8. 기존 데이터 migration 보존, cursor 재개/공백 처리, 키/비공개 상태의 Git·로그 비포함.

전면 회귀·실제 모델 실행/과금 테스트를 매 단계 반복하지 않는다.
관련 단위 테스트와 한 번의 통합 수용 시나리오를 우선한다. 운영 배포는 별도 확인 후 진행한다.

## 범위 밖

사용자 로그인·회원 관리·Nunchi/RBAC, 개인별 비밀 접근, 비용/환율/청구 계산,
Obsidian·Jira·Wiki·SIEM connector, AWS 배포, 임의 셸 전수 수집,
자동 소스 백업·원격 worker 실행·무조건 자동 인수는 포함하지 않는다.
